# Security Policy

VELUM работает с данными, защищёнными адвокатской тайной (ст. 8 ФЗ-63 «Об адвокатской деятельности»), и спроектирован по принципу **privacy by design**. Этот документ описывает модель угроз верхнего уровня и процедуру сообщения об уязвимостях.

## Поддерживаемые версии

Поскольку VELUM находится на ранней стадии, security fixes выходят только для последней версии:

| Версия | Поддержка |
|--------|-----------|
| 0.1.x  | ✅ |
| < 0.1  | ❌ |

## Принципы безопасности

VELUM построен вокруг четырёх неприкосновенных принципов:

1. **Анонимизация только локально.** Чувствительные данные никогда не покидают периметр (ноутбук разработчика, рабочую станцию, серверы ЕПАМ).
2. **Mapping table только в памяти.** Реестр сущностей (соответствие реальных данных и плейсхолдеров) хранится в оперативной памяти, защищённой `mlock()`, шифруется AES-256-GCM, очищается через `sodium_memzero` при закрытии сессии.
3. **Облачные LLM получают только обезличенный текст.** Никаких реальных ФИО, ИНН, адресов или сумм в API-запросах к Claude/GPT/Gemini.
4. **Логи без PII.** Whitelist полей: timestamp, user_id, action_type, doc_id, метаданные API-вызовов. Никогда: оригинальный текст, mapping, ключи.

Любой код, нарушающий хотя бы один из этих принципов, считается **критической уязвимостью** и должен быть отвергнут на ревью.

## Что считается уязвимостью

**Критические:**
- Утечка реальных данных в облачные LLM API
- Утечка mapping table или master key в логах, файлах, дампах
- Возможность recover оригинального текста из публичных артефактов
- Bypass анонимизации (некоторые сущности уходят в сыром виде)

**Высокие:**
- Хранение секретов в коде или git истории
- Слабая криптография (не AES-256, не GCM, плохой KDF)
- Отсутствие очистки чувствительных данных из памяти
- Возможность внешнего наблюдателя восстановить mapping по timing-атакам

**Средние:**
- Некорректная обработка edge cases в NER, ведущая к пропуску сущностей
- Отсутствие валидации входящих данных в API
- Незащищённое хранение временных файлов

**Низкие:**
- Verbose error messages, раскрывающие внутреннюю структуру
- Устаревшие зависимости без известных CVE

## Сообщение об уязвимости

Поскольку VELUM — внутренний продукт ЕПАМ, security issues сообщаются непосредственно руководителю проекта. **Не публиковать в публичных трекерах.**

Включить в отчёт:
1. Описание уязвимости
2. Шаги воспроизведения
3. Затронутые компоненты
4. Предлагаемое исправление (если есть)
5. Severity (по классификации выше)

## Зависимости и supply chain

- Все зависимости фиксируются с минимальными версиями в `pyproject.toml` / `package.json`
- Регулярная проверка через `pip-audit` (Python) и `npm audit` (Node)
- Pre-commit hook `detect-secrets` для предотвращения коммитов с утечками
- Pre-commit hook `gitleaks` для дополнительной защиты

## Криптография

- **AES-256-GCM** для шифрования mapping table
- **HKDF-SHA256** для деривации сессионных ключей из мастер-ключа
- **Argon2id** для производных ключей из паролей (при добавлении user auth)
- **TLS 1.3** для всех внешних соединений
- Опционально **ГОСТ Р 34.12-2015 (Кузнечик)** для сценариев с требованиями ФСТЭК (в Final-конфигурации)

## API-ключи и секреты

- Хранение **только в .env** (никогда в git)
- В production — через secret manager (Vault / AWS Secrets Manager / российский аналог)
- Ротация при подозрении на компрометацию
- Никогда не передавать в логи, error messages или ответы API

## Roadmap безопасности

| Версия | Что добавится |
|--------|---------------|
| 0.1.0-alpha | Базовое шифрование, политика логирования, gitignore для secrets |
| 0.2.0 (MVP) | RBAC (8 ролей), audit trail (append-only), детальная политика данных |
| 1.0.0 (Final) | Соответствие 152-ФЗ, опциональная ГОСТ-криптография, формальный security audit, penetration testing |

## Исключения и known limitations

На текущем этапе (Alpha) VELUM используется одним разработчиком в исследовательских целях. Соответственно:
- Нет полноценного RBAC (single-user mode)
- Нет append-only audit trail с hash-chain (добавится в v2.0)
- Нет соответствия 152-ФЗ как продукта (см. [`docs/SECURITY_MODEL.md`](docs/SECURITY_MODEL.md))

Эти ограничения — осознанный выбор для скорости разработки. Архитектура спроектирована так, что compliance-фичи добавляются как расширения, а не как переделка.
