# ADR-0002: Three-layer NER pipeline (regex + NER + LLM)

**Дата:** 2026-04-09
**Статус:** Accepted
**Авторы:** EPAM Legal Dev

## Контекст

CLEARGATE должен анонимизировать чувствительные данные в русскоязычных юридических документах с очень высокой полнотой (recall) — пропуск даже одной сущности может привести к утечке данных в облачную LLM. При этом нужна разумная точность (precision) — слишком много ложных срабатываний делают ревью утомительным для юриста.

Российский юридический контекст добавляет специфику:
- ИНН, ОГРН, СНИЛС, паспорта РФ — структурированные идентификаторы с контрольными суммами
- Русские имена с богатой морфологией (падежи, склонения)
- Названия организаций с юридическими формами (ООО, АО, ЗАО)
- Адреса по российским правилам (улица, дом, корпус, литера)
- Сложные составные сущности («генеральный директор ООО „Ромашка" Иванов И.И.»)

Подходы, которые рассматривались:
1. Только regex → быстро, но не покрывает неструктурированные сущности
2. Только NER (одна модель) → пропускает тонкие случаи
3. Только LLM → дорого, медленно, недетерминированно
4. Комбинация всех трёх

## Решение

Использовать **трёхслойный pipeline**, где каждый последующий слой добавляет сущности к результату предыдущего:

1. **Regex-уровень** — структурированные данные (ИНН, ОГРН, СНИЛС, паспорта, телефоны, email, банковские счета)
2. **NER-уровень** — нейросетевые модели (spaCy ru_core_news_lg для PER/LOC/ORG + GLiNER для zero-shot custom entities)
3. **LLM-уровень** — локальная LLM (Qwen 2.5) для сложных случаев: кореференция, составные сущности, контекстная верификация

## Альтернативы, которые рассматривались

### Только regex
- ✅ Быстро и детерминированно
- ❌ Не покрывает имена, организации, адреса в свободной форме
- ❌ Recall неприемлемо низкий

### Только spaCy (или другая одиночная NER модель)
- ✅ Простая интеграция
- ✅ Достаточно быстро
- ❌ Пропускает структурированные идентификаторы (ИНН и т.п. требуют валидации контрольных сумм)
- ❌ Не обрабатывает кореференцию
- ❌ F1 ~93%, что значит ~7% пропусков — недопустимо для PII

### Только LLM (локальная или облачная)
- ✅ Самое высокое качество в идеале
- ❌ Не может анализировать данные облачно по определению задачи
- ❌ Локальная LLM на каждом запросе медленная (секунды)
- ❌ Недетерминированно (одни и те же данные могут анонимизироваться по-разному)
- ❌ Сложно валидировать структурированные ID

### Fine-tuned BERT на юридическом корпусе
- ✅ Высокая точность для целевого домена
- ❌ Требует размеченного датасета (нет на старте)
- ❌ Долго обучать, дорого валидировать
- 🔄 Запланировано для Final v3.0 как замена spaCy

## Последствия

### Положительные
- Каждый слой закрывает слабости предыдущего
- Regex даёт 100% precision на структурированных ID благодаря валидации контрольных сумм
- spaCy обеспечивает базовое покрытие имён/организаций
- GLiNER позволяет добавлять кастомные сущности без обучения (zero-shot)
- LLM-слой ловит тонкие случаи, недоступные другим подходам
- Можно постепенно отключать слои на сильных конфигурациях (Final), либо включать дополнительные

### Отрицательные / компромиссы
- Сложнее, чем одна модель → больше точек отказа
- Несколько моделей в памяти → больше ресурсов (но в Alpha-конфиге всё помещается в 8 ГБ VRAM)
- Нужно правильно мерджить результаты слоёв (см. ADR-0005 EntityRegistry)
- Метрики качества нужно считать для всего pipeline, а не для отдельных моделей

### Нейтральные
- Время обработки — суммарное от всех слоёв, ~8–12 сек на 10 страниц на Alpha. Приемлемо.

## Метрики качества

Целевые метрики на synthetic test set (50 документов с известной разметкой):
- **Recall**: ≥ 99% (пропускать ≤ 1 из 100 сущностей)
- **Precision**: ≥ 90% (≤ 1 из 10 — ложное срабатывание, юрист отклонит при ревью)
- **Время обработки** (10 страниц): ≤ 12 сек на Alpha, ≤ 4 сек на MVP
