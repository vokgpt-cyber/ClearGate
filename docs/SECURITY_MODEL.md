# Security Model — CLEARGATE

## Назначение

Этот документ описывает модель угроз CLEARGATE, классификацию защищаемых активов, ключевые контрмеры и допущения о доверии. Он предназначен для понимания, **почему** код устроен именно так — даже там, где это кажется избыточным.

## Активы (assets)

| Актив | Класс | Где живёт |
|-------|-------|-----------|
| **Оригинальный текст документа** | КРИТИЧЕСКИЙ | RAM backend во время сессии, никогда на диске без явной воли пользователя |
| **Mapping table** (плейсхолдер ↔ реальное значение) | КРИТИЧЕСКИЙ | RAM backend, AES-256-GCM шифрование, mlock |
| **Master key** | КРИТИЧЕСКИЙ | `.env` (Alpha) / Vault (Final), никогда в git, никогда в логах |
| **Session keys** (производные) | КРИТИЧЕСКИЙ | RAM, время жизни сессии |
| **API ключи LLM провайдеров** | ВЫСОКИЙ | `.env` / Vault |
| **Анонимизированный текст** | СРЕДНИЙ | RAM, передаётся в облачные LLM API |
| **Метаданные сессий** (счётчики, статистика) | НИЗКИЙ | Логи, БД аудита |
| **Исходный код проекта** | СРЕДНИЙ | git репозиторий, бэкапы |
| **ML модели** | НИЗКИЙ | Локальный диск, скачиваются заново при необходимости |

## Принципы безопасности

CLEARGATE построен вокруг **четырёх неприкосновенных принципов**. Любой код, нарушающий хотя бы один — критическая уязвимость.

### 1. Анонимизация только локально

Чувствительные данные **никогда не покидают периметр**:
- Alpha — ноутбук разработчика
- MVP — рабочая станция в офисе ЕПАМ
- Final — серверы в дата-центре ЕПАМ

Облачные LLM API получают **только** обезличенный текст с плейсхолдерами `[ЛИЦО_1]`, `[ИНН_1]` и т.п.

### 2. Mapping table только в памяти

Реестр сущностей (соответствие плейсхолдеров реальным значениям) — **самые чувствительные данные системы**. Тот, кто получит mapping и анонимизированный текст, может полностью восстановить оригинал.

Защита:
- Хранение в RAM с `mlock()` для предотвращения выгрузки в swap
- Шифрование AES-256-GCM с сессионным ключом
- Сессионный ключ — производный от мастер-ключа через HKDF-SHA256
- Очистка через `sodium_memzero` при закрытии сессии
- Опциональный disk cache — **только** в зашифрованном виде с TTL

### 3. Облачные LLM получают только обезличенный текст

Никаких реальных ФИО, ИНН, адресов, сумм в API-запросах к Claude/GPT/Gemini. Это **проверяется автоматически** через unit тесты и pre-commit hooks.

### 4. Логи без PII

Whitelist полей для логирования:
- ✅ timestamp
- ✅ user_id (анонимизированный)
- ✅ session_id (UUID)
- ✅ doc_id (UUID)
- ✅ action_type
- ✅ entity_count, stats by type
- ✅ метаданные API-вызовов (модель, токены, стоимость)
- ✅ duration, latency
- ✅ HTTP коды ответов

**Никогда не логируется:**
- ❌ Оригинальный текст документов
- ❌ Mapping table или её фрагменты
- ❌ Содержимое EntityRegistry
- ❌ Master key, session keys, API keys
- ❌ Полные ответы Cloud LLM (даже анонимизированные)
- ❌ Имена файлов клиентов (могут содержать ФИО)

## Векторы атаки

### A1: Утечка данных через облачные LLM

**Угроза:** Реальные данные клиента попадают в API запрос → утечка в Cloud LLM → потенциальная утечка третьим лицам.

**Контрмеры:**
- NER pipeline с целевым recall ≥99%
- Юрист ревьюит каждую сущность перед отправкой
- Confirmation dialog перед отправкой с показом анонимизированного текста
- Unit тесты проверяют, что в исходящих API запросах нет паттернов реальных данных
- Логи API-вызовов содержат только анонимизированный текст для аудита

**Остаточный риск:** Pipeline пропускает 1 из 100 сущностей. Митигируется ревью пользователем.

### A2: Утечка mapping table из памяти

**Угроза:** Атакующий получает дамп RAM процесса → читает mapping table → восстанавливает оригинальные данные.

**Контрмеры:**
- Mapping table зашифрована AES-256-GCM в RAM
- `mlock()` предотвращает выгрузку в swap
- `sodium_memzero` очищает буферы при закрытии сессии
- Сессионный ключ существует только в RAM, не пишется на диск
- Дополнительный слой: ОС-уровень защиты от core dumps

**Остаточный риск:** Атакующий с root правами и debugger всё ещё может прочитать ключ из памяти. Митигируется тем, что CLEARGATE работает в защищённом окружении (не на чужой машине).

### A3: Утечка master key из .env

**Угроза:** `.env` файл попадает в git, бэкап в облако, в логи через ошибку.

**Контрмеры:**
- `.env` в `.gitignore`
- Pre-commit hook `detect-secrets` блокирует коммиты с потенциальными секретами
- Pre-commit hook `gitleaks` дополнительная проверка
- Бэкапы шифруются с независимой passphrase
- Master key никогда не передаётся в логи (whitelist подход)
- В Final — Vault вместо .env

**Остаточный риск:** Человеческий фактор. Митигируется обучением + автоматизацией.

### A4: Утечка через временные файлы

**Угроза:** При парсинге DOCX/PDF создаются временные файлы с реальными данными → не удаляются → утекают.

**Контрмеры:**
- Парсинг в памяти (через `BytesIO`), без записи на диск
- Если требуется временный файл — `tempfile.NamedTemporaryFile()` с автоудалением
- При завершении сессии — проверка, что в `tmp/` нет файлов сессии

### A5: Side-channel атаки на API timing

**Угроза:** Атакующий измеряет время ответов API → выводит длину mapping table → предположения о содержании.

**Контрмеры:**
- Constant-time сравнения для критичных операций (HMAC, паролей)
- Padding в API responses
- Rate limiting на уровне backend

**Остаточный риск:** Низкий для on-premise сценария.

### A6: Supply chain атаки через зависимости

**Угроза:** Скомпрометированная версия библиотеки (anthropic, openai, presidio) добавляет код, отправляющий данные третьим лицам.

**Контрмеры:**
- Версии зависимостей фиксируются в `pyproject.toml` / `package-lock.json`
- Регулярная проверка через `pip-audit` и `npm audit`
- Минимальный набор зависимостей (нет лишних библиотек)
- Pre-commit hook `gitleaks` ловит подозрительные изменения
- Code review через Claude Code на каждый bump dependency

### A7: SQL injection / XSS / CSRF

**Угроза:** Стандартные web уязвимости.

**Контрмеры:**
- ORM не используем (если потребуется БД — Pydantic + параметризованные запросы)
- FastAPI Pydantic валидация всех входов
- React автоматически экранирует JSX контент
- Tauri capability config ограничивает доступ к системе
- CORS настроен whitelist origins
- CSRF tokens для state-changing запросов (на MVP+)

### A8: Insider threat

**Угроза:** Сам разработчик / пользователь сливает данные.

**Контрмеры (на этапе Alpha — минимальные):**
- Audit log всех действий пользователя
- Logging без PII не позволяет случайно увидеть данные

**На MVP+:** RBAC, разделение ролей, audit trail с hash-chain.

## Что НЕ защищено (известные ограничения)

На текущем этапе (Alpha) CLEARGATE **не защищает от**:

1. **Скомпрометированной ОС** — если атакующий получил root на машине, всё проиграно
2. **Физического доступа** к работающему приложению — атакующий может скопировать RAM
3. **Малвари в браузере** — если Tauri WebView заражён, frontend под угрозой
4. **Атак на сами LLM провайдеры** — если Anthropic/OpenAI/Google скомпрометированы, наш анонимизированный текст всё равно у них
5. **Social engineering** — никакая криптография не защитит от добровольной выдачи паролей

Эти ограничения **осознанные** для текущей фазы. Они частично адресуются на MVP/Final.

## Криптография

### Используемые алгоритмы

| Назначение | Алгоритм | Параметры |
|------------|----------|-----------|
| Шифрование mapping table | AES-256-GCM | 96-bit nonce, без AAD |
| Деривация session key | HKDF-SHA256 | salt = session_id, info = "cleargate-mapping-table-v1" |
| Деривация key из пароля (бэкапы) | PBKDF2-HMAC-SHA256 | 100 000 итераций |
| TLS внешних соединений | TLS 1.3 | стандартные cipher suites |
| Очистка памяти | sodium_memzero | через pynacl |

### Что НЕ используем (специально)

- ❌ DES, 3DES, RC4 — устаревшие
- ❌ MD5, SHA-1 — уязвимы к коллизиям
- ❌ ECB mode — нет семантической безопасности
- ❌ Custom crypto — никогда не пишем свою криптографию
- ❌ Hardcoded ключи — все ключи через env / Vault

### Опциональная ГОСТ-криптография (Final)

В Final-конфигурации опционально доступна ГОСТ Р 34.12-2015 (Кузнечик) для сценариев, где требуется соответствие ФСТЭК. Реализуется через библиотеку `pygost` или нативный C-код. На Alpha/MVP не используется — overhead не оправдан.

## Threat modelling процесс

При добавлении новой фичи задавай вопросы:

1. **Какие новые активы появляются?** Их класс?
2. **Кто/что может на них покушаться?** (insider, outsider, supply chain, side-channel)
3. **Какие контрмеры уже есть?** Достаточно ли?
4. **Какие тесты подтверждают защиту?**
5. **Что в логах? Точно нет PII?**

Если ответ хотя бы на один вопрос «не знаю» — пишем ADR с обсуждением.

## Reporting

Уязвимости сообщаются непосредственно руководителю проекта. Формат:
1. Описание
2. Шаги воспроизведения
3. Затронутые компоненты
4. Severity (critical/high/medium/low)
5. Предлагаемое исправление

См. `SECURITY.md` (root level) для полной процедуры.
